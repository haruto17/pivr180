# 0004. editor は Tauri で構築し、変換は Rust、UI は Svelte で実装する

## ステータス

承認

## コンテキスト

[0001](./0001-record-on-pi-process-on-mac.md) により、変換・合成・補正は Mac 上の editor で行う。editor には、Pi からの取り込み（rsync）、撮影一覧、左右それぞれのイメージサークル中心・半径・回転の手動補正とプレビュー、SBS 正距円筒 180° の書き出し、viewer 配信が求められる（[plan.md](../plan.md)）。

4056×3040 の魚眼画像 2 枚を高速に変換できる処理基盤と、補正をインタラクティブに行える UI を選ぶ必要がある。

## 決定

- editor は **Tauri** で構築する。
- 変換処理は **Rust**（image ＋ rayon、LUT による remap）で実装する。後続のキャリブレーションは opencv-rust を使う。
- UI は **Svelte ＋ TS ＋ Vite** で実装する。プレビューは画面側で縮小画像を WebGL で変換し、本書き出しは Rust で行う。

## 検討した選択肢

### アプリ基盤: Python FastAPI のローカル Web アプリ

- 利点: device と同じ Python で書け、画像処理ライブラリが豊富。
- 欠点: ブラウザ越しのためファイル操作や rsync 実行などのデスクトップ統合が弱い。Python ランタイムの配布・管理が必要になる。

### アプリ基盤: SwiftUI

- 利点: Mac ネイティブで、性能・統合ともに良い。
- 欠点: Mac 専用となり、Web 技術で書く viewer と UI・知見を共有しにくい。

### アプリ基盤: PySide

- 利点: Python でデスクトップアプリを作れる。
- 欠点: 配布が重く、UI 開発の効率が Web 技術に劣る。

### アプリ基盤: Tauri（採用）

- 利点: Rust による高速な処理とデスクトップ統合、Web 技術による UI を両立できる。viewer と同じ Svelte/TS/Vite を使える。
- 欠点: Rust とフロントエンドの 2 言語構成となり、両者の連携（コマンド呼び出し）の設計が必要。

### 変換処理: Python サイドカー

- 利点: Python の画像処理エコシステムを利用できる。
- 欠点: Python ランタイムの同梱・プロセス管理が必要になり、構成が複雑になる。

### 変換処理: WebGPU 変換

- 利点: GPU で高速に変換できる。
- 欠点: 高解像度の本書き出しや JPEG エンコードをフロント側で扱う負担が大きい。

### 変換処理: Rust（image ＋ rayon、LUT remap）（採用）

- 利点: Tauri のバックエンドで直接実行でき、rayon による並列化と LUT の再利用で高速に変換できる。単体テストを書きやすい。
- 欠点: 後続のキャリブレーションには opencv-rust の導入が必要になる。

### UI: React

- 利点: エコシステムが大きく情報が多い。
- 欠点: 本プロジェクトの規模に対して記述量が多くなりやすい。

### UI: Svelte ＋ TS ＋ Vite（採用）

- 利点: 記述が簡潔で、viewer と技術スタックを共通化できる。
- 欠点: React と比べてエコシステムが小さい。

## 結果 / 影響

- 高速な変換とインタラクティブな補正 UI を 1 つのデスクトップアプリで提供できる。
- プレビュー（WebGL）と本書き出し（Rust）で変換実装が 2 系統になり、結果の一致を保つ必要がある。Rust 側は合成魚眼画像を用いた単体テストで変換精度を検証する。
- Rust とフロントエンドの 2 言語構成のコストを受け入れる。
