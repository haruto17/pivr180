# 0012. 動画撮影の方式

## ステータス

提案

## コンテキスト

[0002](./0002-photo-only-mvp-jpeg-quality-100.md) で、MVP は写真のみとし、動画は後続のマイルストーンに延期すると決めた。0002 では、動画は 2028×1520 のビニングで撮り、CPU の H.264 か非圧縮の YUV かをベンチマークで決めるとした。Pi 5 には H.264 のハードウェアエンコーダーがないため、エンコードは CPU で行うか、Pi では行わずに Mac で行うかのどちらかになる（[0001](./0001-record-on-pi-process-on-mac.md) で、Pi は記録のみを担い、変換は Mac で行うと決めている）。

[0011](./0011-control-camera-from-android-app-over-aoa.md) で、Android アプリに撮影モードの項目を設け、当面は写真のみとし、動画は M10 で扱うと決めた。M10 では、動画撮影の方式をベンチマークで決め、アプリから撮影モードを動画に切り替えて撮れるようにする（[milestone.md](../milestone.md#m10-device-動画)）。

いまの撮影ソフトは次のとおり動いている。

- 左右のカメラを Picamera2 で開き、4056×3040 の静止画の設定（`create_still_configuration`）、10 fps で動かし続ける。プレビュー用に 640×480 の lores を出す。
- libcamera の `rpi.sync` で左右のフレームのタイミングを揃え、シャッター時はセンサーのタイムスタンプが最も近い左右のフレームを組にする。時刻差が 1ms を超えたら最大 3 回撮り直す（[0003](./0003-software-sync-and-copy-exposure-wb.md)）。`rpi.sync` はデフォルトルートがないとマルチキャストのグループに参加できず、同期が取れない（#121）。
- 同期が取れるまでに 70 フレームを待つ。設定を変えてカメラを起動し直すと、同期を待ち直す必要がある。
- 露出/WB は、プレビュー中に左カメラの値を右カメラへ随時コピーし、シャッター時に左右とも固定する（0003）。
- 撮影ごとに `/data/captures/<YYYYMMDD-HHMMSS-NNN>/{left.jpg,right.jpg,meta.json}` を NVMe（500GB）に保存する。`meta.json` は `schema/meta.schema.json`（`schema_version` は 1）に従い、左右のセンサー時刻、時刻差、撮り直しの回数、露出/WB の値を持つ。

動画では、写真にはなかった次の制約がある。

- 撮り直しができない。左右の時刻差が大きいフレームがあっても、そのまま記録するか捨てるしかない。
- 処理の量が時間に比例する。エンコード、書き込み、発熱が録画中ずっと続き、1 つでも追いつかなければフレームが落ちる。
- 2028×1520 の YUV420 は 1 フレームで約 4.6 MB になる。30 fps で左右を記録すると、およそ 280 MB/s になる（見積もり。ストライドの詰め物は含まない）。

この ADR では、動画撮影の方式を決めるための論点と選択肢、ベンチマークで測ることをまとめる。結論はベンチマークの結果を見てから書き、ステータスを「承認」にする。

## 決定

まだ決めていない。次の「ベンチマークで測ること」の結果を見て、論点ごとに選択肢を選ぶ。

## ベンチマークで測ること

エンコード（CPU の H.264、YUV の生データ、MJPEG）と、解像度・フレームレートの候補の組み合わせごとに、実機で左右同時に録画して測る。筐体（M8）に収めた状態で、室温と屋外を想定した条件で、少なくとも 10 分続けて録画する。

| 項目 | 測り方の例 | 判断の目安（案） |
|---|---|---|
| CPU 使用率 | `pidstat` などで、撮影ソフトとエンコードのプロセスの使用率をコアごとに記録する | プレビューの配信と SPI ディスプレイの描画を同時に動かしても、余裕がある |
| 書き込み速度 | `iostat` などで NVMe への書き込み速度を記録し、`dd` などで測った NVMe の上限と比べる | 必要な速度が上限を十分に下回り、書き込みの遅れでフレームが落ちない |
| 温度 | `vcgencmd measure_temp` と `vcgencmd get_throttled` で、SoC の温度とスロットリングの有無を記録する | 10 分以上の録画で、スロットリングが起きない |
| 左右のずれ | フレームごとのセンサー時刻から、左右の時刻差の平均・最大、1ms を超えた割合を求める | ほとんどのフレームで 1ms 以内に収まる |
| フレームの欠け | フレームごとのセンサー時刻の間隔から、落ちたフレームの数を数える | 10 分の録画で落ちない |
| 録画できる時間 | 1 秒あたりのデータ量から、NVMe の空き容量で録画できる時間を求める。温度で止まる場合はその時間も記録する | 1 回の撮影に必要な長さ（数分）を満たす |

判断の目安は、ベンチマークの前に見直してよい。ADR を「承認」にするときに、測った値と選んだ理由を書く。

## 検討した選択肢

### 論点 1: エンコード

#### CPU で H.264 にエンコードする

Picamera2 の libav を使ったエンコーダーなどで、Pi の CPU で H.264 にエンコードして記録する。

- 利点: ファイルが小さく、書き込み速度と NVMe の容量に余裕が出る。長い時間を録画できる。一般のプレイヤーでそのまま再生できる。
- 欠点: 2028×1520 を 2 本同時にエンコードすると、CPU の負荷と発熱が大きい。間に合わなければフレームが落ちる。CPU を使い切ると、プレビューの配信や SPI ディスプレイの描画（[0010](./0010-spi-display-for-last-capture-and-status.md)）にも影響する。画質を保つには高いビットレートが必要になる。Pi で圧縮するため、Mac での補正（魚眼から正距円筒への変換）の前に画質が落ちる。

#### YUV の生データを保存し、Mac で変換する

ISP が出した YUV420 のフレームをそのまま保存し、Mac（editor）で取り込んでからエンコードする。

- 利点: Pi の CPU をほとんど使わず、発熱が小さい。圧縮による劣化がない。Pi は記録のみを担う 0001 の方針に合う。
- 欠点: 30 fps で左右およそ 280 MB/s と、データ量が大きい。NVMe の書き込みと容量の両方が厳しく、500GB でも 30 分ほどしか録れない。Pi から Mac への取り込み（rsync）にも時間がかかる。editor に YUV の読み込みとエンコードの処理が必要になる。

#### CPU で MJPEG にエンコードする

フレームごとに JPEG にして保存する。H.264 と YUV の中間の案として挙げる。

- 利点: H.264 よりエンコードが軽い見込みがある。フレームごとに独立しているため、フレームの欠けや左右の組み合わせを扱いやすい。editor が JPEG を扱う処理を流用できる。
- 欠点: H.264 よりファイルが大きい。CPU の負荷と発熱は残る。一般のプレイヤーでの再生には、Mac で変換が必要になる。

### 論点 2: 解像度とフレームレート

IMX477 は、センサーのモードとして 4056×3040（最大 10 fps 程度）、2028×1520 の 2×2 ビニング（最大 40 fps 程度）、2028×1080 や 1332×990 のクロップ（より高いフレームレート）を持つ。レンズ（Entaniya RP-L190HQ）のイメージサークルは 4.6mm で、センサーの短辺とほぼ同じ大きさのため、クロップのモードではイメージサークルの上下が切れる。

#### 2028×1520（2×2 ビニング）で 30 fps

- 利点: イメージサークル全体が写る。一般的なフレームレートで、動きが滑らかに見える。
- 欠点: 片目が約 2028 画素で、写真（4056×3040）や書き出し（片目 約 2880×2880）より解像度が低い。エンコードの負荷とデータ量は、24 fps より大きい。

#### 2028×1520（2×2 ビニング）で 24 fps など、低いフレームレート

- 利点: エンコードの負荷とデータ量を 30 fps より 2 割ほど減らせる。
- 欠点: 動きの速い被写体や、頭を動かしたときの見え方が 30 fps より劣る可能性がある。Quest 3 での見え方を確かめる必要がある。

#### 4056×3040 で 10 fps

- 利点: 写真と同じ解像度で、いまのカメラの設定をそのまま使える。
- 欠点: 10 fps では動画として滑らかに見えない。データ量とエンコードの負荷が最も大きい。

### 論点 3: 保存の形式と `meta.json` の扱い

#### 写真と同じ `captures/` に、撮影ごとのディレクトリとして保存する

`/data/captures/<YYYYMMDD-HHMMSS-NNN>/` に、左右の動画（例: `left.mp4`、`right.mp4`）、フレームごとのタイムスタンプ、`meta.json` を置く。

- 利点: ディレクトリの名前の付け方、一覧、削除、取り込み（rsync）の仕組みをそのまま使える。
- 欠点: 写真と動画が混ざるため、editor の一覧（M5）とスマホ Web UI の撮影一覧で、種類を見分ける必要がある。

#### 動画を `captures/` とは別のディレクトリに保存する

- 利点: 写真の一覧や取り込みの処理に影響しない。
- 欠点: 一覧・削除・取り込みの仕組みを動画のために作り直すか、2 か所を扱うように変える必要がある。

#### `meta.json` に撮影の種類を加え、`schema_version` を上げる

- 利点: 1 つの schema で写真と動画を扱える。種類で見分ければ、既存の処理を少しずつ動画に対応させられる。
- 欠点: いまの schema は `sync` に写真の撮り直しの回数を必須としているため、写真と動画で必須の項目を分ける変更が必要になる。editor の読み込みも `schema_version` 2 に対応させる必要がある。

#### 動画用に別の schema を作る

- 利点: 写真の schema を変えずに済む。動画に必要な項目だけを持てる。
- 欠点: 共通の項目（カメラの情報、露出/WB）を 2 か所で管理する。

#### フレームごとのタイムスタンプの置き場所

- `meta.json` に入れる: ファイルが 1 つで済むが、30 fps で 1 分録ると左右で 3,600 件になり、`meta.json` が大きくなる。
- 別のファイル（例: `left_timestamps.txt`）に入れる: `meta.json` を小さく保てる。録画中に 1 行ずつ追記できるため、途中で電源が落ちても残る。ファイルの書式を別に決める必要がある。

### 論点 4: 左右の同期

`rpi.sync` で左右のフレームのタイミングを揃える点は、写真と同じとする（0003）。そのうえで、フレームごとのタイムスタンプの扱いを決める。

#### 左右をそれぞれ全フレーム記録し、Mac で組にする

左右のフレームごとのセンサー時刻を記録し、editor で時刻が最も近いフレームを組にする。

- 利点: Pi の処理が単純で、録画中の負荷が小さい。組み方を後から変えられる。
- 欠点: editor に組み合わせの処理が必要になる。片方だけでフレームが落ちた場合の扱いを editor で決める必要がある。

#### Pi で組にし、組にならなかったフレームを捨てる

録画中に左右のフレームを時刻で組にし、時刻差が大きいフレームや片方だけのフレームは記録しない。

- 利点: 保存した動画は左右のフレームが 1 対 1 で対応し、editor が単純になる。
- 欠点: 録画中の処理と、左右のフレームを待つためのバッファーが増える。捨てたフレームの分だけ動画が飛ぶ。

#### 時刻差の記録

撮り直しができないため、写真の「1ms を超えたら撮り直す」は使えない。代わりに、時刻差の平均・最大と、1ms を超えたフレームの数を `meta.json` に記録し、超えたフレームがあれば警告とする案がある。

#### 録画中の露出/WB

- 録画の開始時に左右とも固定する: 左右が録画中ずっと一致する。明るさが変わる場面では、露出が追従しない。
- 録画中も左カメラの値を右カメラへコピーし続ける: 明るさの変化に追従する。コピーが右カメラに反映されるまでの数フレームの間、左右の露出がずれる。

### 論点 5: アプリからの撮影モードの切り替えと、録画の開始・停止

ADR 0011 で決めたアプリの撮影モードの項目に、動画を加える。

#### 撮影モードの切り替え

- アプリからのみ切り替える: 操作の場所が 1 つで分かりやすい。外出先でアプリがないと切り替えられない。
- アプリと AtomS3 Lite のボタン（[0008](./0008-atoms3-lite-usb-shutter-and-status.md)）の両方で切り替える: アプリがなくても切り替えられる。ボタンの押し方（短押し・長押し）の割り当てが増え、誤操作しやすくなる。

写真と動画でカメラの設定が違うため、切り替えのたびにカメラを止めて設定し直し、同期を待ち直す（いまは 70 フレーム）。切り替えに数秒かかることを、アプリと SPI ディスプレイで知らせる必要がある。

#### 録画の開始・停止

- 動画モードでは、AtomS3 Lite のボタンを押すと録画を始め、もう一度押すと止める: 写真と同じ操作で撮れる。長押しのシャットダウン（M3-1）と区別するため、押した直後ではなく離したときに開始・停止を判断する必要がある。
- アプリのボタンで開始・停止する: 録画の時間や残りの容量をアプリで見ながら操作できる。アプリがないと録画できない。
- 両方で開始・停止できるようにする: どちらからでも操作できる。両方から同時に操作されたときの扱いを決める必要がある。

#### 録画中の表示と停止の扱い

- AtomS3 Lite の LED に「録画中」の状態を加えるか、いまの「撮影中」で表すかを決める。加える場合は、ファームウェアのメッセージの書式（M3-6）を変える。
- SPI ディスプレイに、録画の経過時間と残りの時間を表示する。
- 空き容量が足りなくなったときと、録画中にシャットダウンするとき（長押し・アプリ）は、録画を止めてファイルを閉じてから続ける。

## 結果 / 影響

- ベンチマークで方式を決めてから、録画を実装する。決まるまでは、アプリの撮影モードは写真のみのままとする（ADR 0011）。
- どの方式を選んでも、写真と動画でカメラの設定を切り替える処理と、同期を待ち直す処理が撮影ソフトに加わる。
- `meta.json` の schema を変える場合は、device と editor の両方の対応が必要になる。
- YUV の生データを選ぶと、NVMe の容量と取り込みの時間が録画できる長さを決める。CPU でエンコードする方式を選ぶと、温度とスロットリングが録画できる長さを決める。筐体（M8）の放熱の設計にも影響しうる。
- 音声は、この ADR では扱わない（[plan.md](../plan.md#後続マイルストーン候補) の別の候補とする）。
