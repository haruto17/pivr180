# 0010. 撮影結果は SPI ディスプレイ Adafruit 4313 で本体に表示して確認する

## ステータス

置き換え（0011 により）

## コンテキスト

外出先では、撮影できたか（左右とも写っているか、エラーが起きていないか）をその場で確かめたい。[0008](./0008-atoms3-lite-usb-shutter-and-status.md) で、シャッターボタンと状態表示には AtomS3 Lite を使うと決めた。AtomS3 Lite の RGB LED では状態の種類しか分からず、撮影した画像やエラーの内容は確かめられない。そこで、スマホで撮影結果を確かめる方式を、2026-11-24〜25 に実機で試した。

- **Pi の Wi-Fi アクセスポイント**（NetworkManager の `pivr180-ap`、WPA2）: Android で SSID は見えるが、接続は Pi まで届かなかった（`iw dev wlan0 station dump` が空で、ログにも何も出ない）。PMF の設定を変えても直らなかった。また、デフォルトルートがないと libcamera の `rpi.sync` がマルチキャストのグループに参加できず、左右のカメラの同期が取れない（#121 で別に扱う）。
- **有線の直結**（Android に USB-C の LAN アダプタを挿し、Pi 5 の `eth0` につなぐ。Pi 側は `ipv4.method shared` で `10.42.1.1`）: ライブプレビューを表示できたことはあったが、接続できるときとできないときがあった（#116、#117 はクローズした）。
- **Bluetooth で縮小画像を送る**（#118）: 実現はできそうだが、手間が大きい（後述）。

0008 では、SPI ディスプレイ Adafruit 4313 を状態表示の候補として検討し、配線が増えること、筐体に表示窓が要ること、撮影ソフトが起動するまで何も表示されないこと、シャッターボタンが別に要ることを理由に採用しなかった（#77, #78）。その後、撮影結果をスマホで確かめる方式がいずれも安定しないか手間が大きいと分かり、本体で撮影した画像を確かめる必要が出てきた。状態表示を置き換えるのではなく、AtomS3 Lite に加える補助の表示として使うなら、0008 で挙げた欠点のうち、起動前の表示とシャッターボタンは AtomS3 Lite で補える。

Adafruit 4313 の仕様は次のとおり。

- 1.3 インチ、240×240 の IPS 液晶。コントローラは ST7789 で、SPI でつなぐ
- 1 フレームは 240×240×16bit で約 115 KB
- MicroSD のスロットを持つ

## 決定

- Pi 5 に **Adafruit 4313** を SPI でつなぎ、撮影結果を確かめるための補助の表示にする。
  - 直前の撮影の左右の縮小画像を並べて表示する。
  - 撮影ソフトの状態（待機中・撮影中・エラー）と、エラーの場合はその内容を短い文字で表示する。
  - 撮影枚数と、保存先の空き容量を表示する。
- シャッターボタンと、起動中・待機中・撮影中・エラー・切断の LED の表示は、これまでどおり AtomS3 Lite で行う（0008 のまま）。
- 配線は SPI0（SCLK: GPIO11、MOSI: GPIO10、CE0: GPIO8）と、DC・RST 用の GPIO、3V3、GND を使う。DC・RST に使う GPIO の番号は、実装（#120）と配線図（#46）で決める。
- Pi 5 では `RPi.GPIO` が使えないため、GPIO は lgpio / gpiod で扱う。ディスプレイを制御するライブラリは #120 で選ぶ。
- ディスプレイの MicroSD スロットは使わない。
- ディスプレイがない、または初期化に失敗した場合でも、撮影は続ける。

## 検討した選択肢

### Pi の Wi-Fi アクセスポイントにスマホをつなぐ

- 利点: ケーブルが要らない。スマホ Web UI（[0009](./0009-web-ui-in-capture-process-on-port-80.md)）のライブプレビューや撮影一覧をそのまま使える。
- 欠点: 実機では、Android の接続が Pi まで届かなかった。PMF の設定を変えても直らなかった。デフォルトルートがないため、カメラの同期も取れなかった（#121）。

### 有線で直結する

- 利点: スマホ Web UI をそのまま使える。Wi-Fi の相性の問題を避けられる。
- 欠点: 実機では、接続できるときとできないときがあった（#116、#117）。Android 用の USB-C の LAN アダプタと LAN ケーブルを持ち歩く必要がある。

### スマホのテザリングに Pi をつなぐ（Wi-Fi / USB）

- 利点: Android 側の接続は安定していると見込める。スマホ Web UI をそのまま使える。
- 欠点: モバイル通信を使うため、採用しない。

### USB の MTP でスマホへ画像をコピーする

- 利点: ネットワークを使わない。
- 欠点: 新しくコードを書く必要がある。コピーのたびにスマホのロックを解除し、ファイル転送を許可する必要がある。Linux の MTP は動作が不安定になりやすい。撮影前のプレビューはできない。Bluetooth で送る方式を優先して、検討をやめた。

### Bluetooth で縮小画像をスマホへ送る（#118）

- 利点: ネットワークもケーブルも使わない。
- 欠点: ペアリングが必要になる。Android が受信のたびに承認を求める場合がある。Pi 側で送信を担う obexd はユーザーのセッションバスで動くため、systemd のサービスから使うのが難しい。新しく書くコードが多い。SPI ディスプレイに置き換えた。

### SPI ディスプレイ Adafruit 4313 で本体に表示する（採用）

- 利点: スマホもネットワークも使わずに、撮影した直後にその場で左右の画像と状態を確かめられる。エラーの内容を短い文字で表示できる。手持ちの部品で済む。起動前の表示とシャッターボタンは AtomS3 Lite が担うため、0008 で挙げた欠点のうち 2 つは問題にならない。
- 欠点: SPI0 と DC・RST 用の GPIO を使うため、配線が増える。筐体に表示窓が必要になる。1.3 インチではピントの細かい確認はできない。

## 結果 / 影響

- 0008 の「GPIO は使わない」を一部見直す。ディスプレイのために SPI0 と DC・RST 用の GPIO を使う。シャッターボタンと状態の LED は、これまでどおり USB でつないだ AtomS3 Lite で扱う。
- 配線図（#46）は、AtomS3 Lite の USB 接続に加えて、ディスプレイの SPI の配線を扱う。筐体（#45、#47）には、ディスプレイの表示窓と固定する場所が必要になる。
- 撮影ソフトは、保存のたびに縮小画像を作り、ディスプレイへ送る処理を持つ。1 フレームは約 115 KB なので、描画が撮影や保存を止めたり遅らせたりしないように、撮影の処理とは分けて行う。実機で影響がないかを確認する。
- 1.3 インチではピントや細部の確認はできない。細部は、自宅で editor に取り込んでから確認する。
- ネットワークにつながっていない状態でもカメラの同期が取れるようにする修正（#121）は、この決定とは別に必要になる。
- スマホ Web UI と、Pi の Wi-Fi アクセスポイントを残すかどうかは、この ADR では決めない。
