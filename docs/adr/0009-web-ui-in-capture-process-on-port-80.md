# 0009. スマホ Web UI は撮影ソフトと同じプロセスで 80 番ポートから配信し、画面のビルド成果物をコミットする

## ステータス

置き換え（0011 により）

## コンテキスト

外出先でスマホからプレビュー・撮影設定・撮影一覧と削除・シャットダウンができるように、device にスマホ Web UI を作る（[plan.md](../plan.md) のスマホ Web UI、[milestone.md](../milestone.md) の M4）。plan.md では、FastAPI で配信し、画面は素の HTML/TS で作ってビルドした成果物を device に同梱すると決めている。#22 で土台を作り、各画面は #23〜#26 で追加する。

土台を作るにあたって、次の 3 点を決める必要があった。

- Web サーバーをどのプロセスで動かすか。カメラ（`CameraPair`）は同時に 1 つのプロセスしか開けない。ライブプレビュー（#23）や撮影設定（#24）は、撮影ソフト `pivr180-capture` がプレビューと撮影に使っているカメラと、露出/WB のコピー（`ExposureSync`）に触る必要がある。撮影ソフトは systemd のサービスとして起動する（#21）。
- 画面の TypeScript をどこでビルドし、成果物をどう Pi に届けるか。Pi では venv と uv だけでセットアップしており（`setup_pi_venv.sh`）、Node.js は入れていない。
- どのポートで配信するか。スマホからは `http://pivr180.local`（#27）で開けるようにしたい。80 番は、root でないユーザーでは通常使えない。撮影ソフトは systemd のユニットで `User=` を指定し、root でないユーザーで動かしている。

## 決定

- **プロセス構成**: Web サーバーは撮影ソフト `pivr180-capture` と同じプロセスで動かす。uvicorn を別スレッドで起動し、FastAPI のアプリから `CameraPair` や `ExposureSync` などを直接共有できるようにする。systemd のユニット（`pivr180-capture.service`）は 1 つのままにする。
  - アプリは `pivr180_device.web.create_app()` で作る。後続の機能は、共有するオブジェクトを引数に取って `APIRouter` を返す関数として作り、`create_app()` に渡す。
  - Web サーバーはカメラを開く前に起動し、カメラとシリアルを解放した後に止める。待ち受けに失敗した場合は、エラーをログに出して Web UI なしで撮影を続ける。
- **ビルド成果物**: 画面のソースは `device/web/` に置く。pnpm と TypeScript を使い、フレームワークは使わない。ビルドには Vite を、テストには Vitest を使う。ビルド結果は Python パッケージ内の `device/src/pivr180_device/static/` に出力し、リポジトリにコミットする。Pi では Node.js を使わない。CI で画面のテストとビルドを行い、コミット済みの成果物がソースのビルド結果と一致するかを確認する。
- **ポート**: 80 番で配信し、`http://pivr180.local` で開けるようにする。systemd のユニットに `AmbientCapabilities=CAP_NET_BIND_SERVICE` を付け、root でないユーザーのまま 80 番を使う。開発や手動での起動のために、`--web-port` で変更できるようにする。

## 検討した選択肢

### プロセス構成

#### Web サーバーを別プロセス・別サービスにする

- 利点: Web サーバーの不具合や再起動が撮影に影響しない。撮影ソフトと独立に開発・起動できる。
- 欠点: カメラは 1 つのプロセスしか開けないため、プレビューの映像や露出/WB の設定を、撮影ソフトとの間でプロセス間通信（ソケット、共有メモリなど）でやりとりする必要がある。通信の取り決めと、systemd のユニットが 2 つになる。

#### 同じプロセスで、uvicorn を別スレッドで動かす（採用）

- 利点: `CameraPair` や `ExposureSync` をそのまま共有でき、プロセス間通信が要らない。systemd のユニットは 1 つで済む。
- 欠点: Web サーバーの処理が重いと、同じプロセスの撮影の処理と CPU や GIL を取り合う。カメラへの同時アクセスを、スレッド間で調停する必要がある（プレビュー中の露出/WB のコピーとの調停は `ExposureSync` が既に行っている）。Web サーバーが原因でプロセスが落ちると、撮影も止まる。

### ビルド成果物

#### Pi 上でビルドする

- 利点: 成果物をコミットしないため、ソースと成果物のずれが起きない。
- 欠点: Pi に Node.js と pnpm を入れ、セットアップ手順に加える必要がある。依存のダウンロードにネットワークが要る。

#### Python のパッケージ（wheel）をビルドする段階で成果物を作る

- 利点: 成果物をコミットしない。
- 欠点: Pi では `uv sync` でリポジトリから直接インストールしているため、結局 Pi で Node.js が要るか、別にパッケージを配布する仕組みが要る。

#### 成果物をリポジトリにコミットする（採用）

- 利点: Pi は `git pull` だけで最新の画面になり、Node.js が要らない。
- 欠点: ソースを変えたときにビルドとコミットを忘れると、成果物が古いままになる。CI で一致を確認して検出する。成果物の差分がレビューに混ざる。

### ビルドツール

#### tsc だけ

- 利点: TypeScript だけで済む。
- 欠点: `index.html` などのコピーや、キャッシュ対策のファイル名の付け替えを自前で行う必要がある。テストに Vitest を使うと Vite も依存に入るため、依存は減らない。

#### Vite（採用）

- 利点: `index.html` を起点に、ハッシュ付きのファイル名でまとめて出力できる。Vitest と設定を共有できる。viewer / editor と同じ道具になる。
- 欠点: tsc だけより設定と依存が多い。

### ポート

#### 8080 などの非特権ポート

- 利点: 権限の設定が要らない。
- 欠点: スマホで `http://pivr180.local:8080` のようにポート番号を入力する必要がある。

#### root で動かして 80 番を使う

- 利点: 設定が単純。
- 欠点: 撮影ソフト全体が root で動き、保存した撮影データの所有者も root になる。`dialout` などのグループや polkit のルールをユーザーに与えている現在の構成（#19, #21）と合わない。

#### iptables / nftables で 80 番を 8080 番に転送する

- 利点: 撮影ソフトに権限を与えなくてよい。
- 欠点: ファイアウォールの設定が増え、Pi のセットアップ手順と管理が複雑になる。

#### `AmbientCapabilities=CAP_NET_BIND_SERVICE` で 80 番を使う（採用）

- 利点: root でないユーザーのまま 80 番を使え、ユニットに 1 行足すだけで済む。スマホではポート番号を入力しなくてよい。
- 欠点: systemd から起動した場合だけ有効になる。`uv run pivr180-capture` で手動で起動する場合は 80 番を使えないため、`--web-port` を指定する必要がある。

## 結果 / 影響

- 後続の #23〜#26 は、`create_app()` に渡すルーターを追加し、撮影ソフトの `main()` から共有するオブジェクトを渡すことで機能を足せる。プロセス間通信や追加のユニットは要らない。
- 撮影ソフトの起動時に Web サーバーも起動する。待ち受けに失敗しても撮影は続けるため、本体のボタンだけで撮影できること（[0008](./0008-atoms3-lite-usb-shutter-and-status.md)）は Web UI に左右されない。失敗はログでしか分からない。
- Web サーバーとプレビュー・撮影が CPU を取り合う。MJPEG の配信（#23）で撮影や同期に影響が出ないかは、実機で確認する。
- 画面のソースを変更したら、`pnpm build` の成果物も一緒にコミットする必要がある。忘れた場合は CI が失敗する。
- device の Python の依存に `fastapi` と `uvicorn` が加わり、Pi の venv が大きくなる。
- `pivr180.local` で開けるかどうかは、ホスト名の設定（#27）に依存する。
