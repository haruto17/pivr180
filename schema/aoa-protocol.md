# AOA のプロトコル

Pi（device）と Android アプリが AOA でやり取りするメッセージの形。方針は [ADR 0011](../docs/adr/0011-control-camera-from-android-app-over-aoa.md)。

プロトコルのバージョンは **1**。

## フレーム

AOA のバルク転送は、どちらの向きもバイト列として扱う。USB のパケットの区切りとフレームの区切りは一致しないので、受け取る側はフレームの長さを見て区切る。

1 つのフレームは、長さ・種類・本文からなる。

| 位置 | 大きさ | 内容 |
|---|---|---|
| 0 | 4 バイト | 長さ: 本文のバイト数。符号なし 32 ビット、ビッグエンディアン |
| 4 | 1 バイト | 種類 |
| 5 | 長さ バイト | 本文 |

- 長さには、長さと種類の 5 バイトを含めない。本文が空のフレームの長さは 0。
- 長さの上限は 4 MiB（4194304）。上限を超える長さを受け取ったら、ストリームが壊れたものとして接続をやり直す。
- 知らない種類のフレームは、長さの分だけ読み飛ばす。

### 種類ごとの本文

| 種類 | 名前 | 向き | 本文 |
|---|---|---|---|
| `0x01` | JSON | 両方 | UTF-8 の JSON オブジェクト 1 つ。[`aoa.schema.json`](./aoa.schema.json) に合う |
| `0x02` | プレビュー | Pi → アプリ | 左右を並べた JPEG |
| `0x03` | サムネイル | Pi → アプリ | `get_thumbnail` の `id`（符号なし 32 ビット、ビッグエンディアン、4 バイト）に続けて JPEG |

プレビューの大きさ・画質・間隔（640x480×2、JPEG 品質 70、最大 5fps）は Pi が決める。アプリは JPEG の大きさを読んで表示する。

### 例

`{"type":"shutter","id":7}`（25 バイト）を送るフレーム:

```
00 00 00 19  01  7b 22 74 79 70 65 22 3a 22 73 68 75 74 74 65 72 22 2c 22 69 64 22 3a 37 7d
長さ=25      JSON 本文
```

（`00 00 00 19` が長さ、`01` が種類、残りが本文）

`id` が 7 の `get_thumbnail` に応えるサムネイルのフレーム（JPEG が N バイトのとき）:

```
長さ=N+4 (4 バイト)  03  00 00 00 07  JPEG (N バイト)
```

### 例のファイル

Pi と Android アプリのフレームの組み立てと分解のテストは、同じ例のファイルを読む。バイト列はすべて小文字の 16 進の文字列で書く。JPEG は本物の画像でなく、`ffd8ffd9`（SOI と EOI だけ）にする。

[`examples/aoa/frames/`](./examples/aoa/frames/) には、フレーム 1 つ分を置く。

| 項目 | 内容 |
|---|---|
| `direction` | `app_to_device` か `device_to_app` |
| `frame` | フレーム全体 |
| `frame_type` | 種類（整数） |
| `body` | 本文 |
| `message` | 種類が `0x01` のときだけ。本文を読んだ JSON オブジェクト |
| `jpeg` | 種類が `0x02`・`0x03` のときだけ。本文の JPEG |
| `thumbnail_id` | 種類が `0x03` のときだけ。本文の先頭の `id` |

組み立てるテストは `body` から `frame` を作り、分解するテストは `frame` から `frame_type` と `body`（と種類ごとの項目）を取り出す。JSON の本文は書き方（空白やキーの順番）が実装ごとに違ってよいので、`message` から本文を作って比べない。

[`examples/aoa/frame_headers/`](./examples/aoa/frame_headers/) には、長さの上限の前後の例を置く。4 MiB の本文は置かず、長さと種類の 5 バイト（`header`）と、`length`・`frame_type`・上限以内かどうか（`within_limit`）だけを書く。

## JSON のメッセージ

すべてのメッセージは `type` を持つ。アプリ → Pi のメッセージは `$defs/app_message`、Pi → アプリのメッセージは `$defs/device_message` で検証する。例は [`examples/aoa/`](./examples/aoa/) に向きごとに置く。

### 要求と応答

アプリ → Pi のメッセージはすべて要求で、アプリが決めた `id`（0〜2147483647）を持つ。Pi は同じ `id` で応答する。応答が届く前に次の要求を送ってよく、応答の順番は要求の順番と同じとは限らない。

| 要求 | 成功したときの応答 |
|---|---|
| `hello` | `welcome` |
| `shutter` | `ok`（撮影の結果は `status` で届く） |
| `get_settings`、`set_settings` | `settings` |
| `get_mode`、`set_mode` | `mode` |
| `list_captures` | `captures` |
| `get_thumbnail` | サムネイルのフレーム（`0x03`） |
| `delete_capture` | `ok` |
| `shutdown` | `ok` |

失敗したときは、どの要求にも同じ `id` の `error` で応える。要求として読めないフレーム（JSON でない、`id` がないなど）には、`id` のない `error` で応える。

### ハンドシェイク

1. アプリは接続したら、最初に `hello` で自分のプロトコルのバージョンを送る。
2. Pi はバージョンが同じなら `welcome` で応え、続けて `status` を送り、プレビューのフレームを送り始める。
3. バージョンが違うときは、`unsupported_protocol_version` の `error` で応え、それ以外の要求には応えない。
4. `hello` の前に届いた要求には、`handshake_required` の `error` で応える。

### 状態

Pi は `status` を要求なしで送る。ハンドシェイクの直後と、どれかの項目が変わったときに送る。`error_message` は `state` が `error` のときだけ持つ。

### バージョンを上げるとき

メッセージや項目を足す・変えるときは、`aoa.schema.json` と例を直し、プロトコルのバージョンを上げる。どのメッセージも知らない項目を受け付けないので、古いアプリと新しい Pi が混ざると、ハンドシェイクで分かる。
